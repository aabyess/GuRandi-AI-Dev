## 워크플로

1. 사용자가 PM에게 지시한다.
2. PM은 조사·분석이 많이 필요하면 쉬고 있는 팀원에게 조사를 맡기고(코딩 금지라고 명시), 결론을 받아 설계를 정한다.
3. PM은 작업을 쪼개 구현담당1/2에게 배정한다. 배정 메시지에는 반드시 포함:
   - 목표, 대상 파일/폴더, 완료 조건, 건드리지 말아야 할 영역
4. 구현담당은 작업 완료 시 PM에게 보고: 변경 파일 목록 + 요약 + 검증 결과.
5. **코드리뷰 규칙**
   - PM이 코딩한 결과 → 구현담당1/2 중 **쉬고 있는 세션**에게 리뷰 요청.
   - 구현담당1/2가 코딩한 결과 → **PM**이 리뷰.
   - 리뷰어는 버그/누락/규칙 위반 위주로 지적하고, 승인 여부를 명확히 답한다.
6. 사용자에게 최종 보고는 PM이 한다.

## 충돌 방지

- 같은 파일을 두 세션이 동시에 수정하지 않는다. PM이 배정 시 파일 소유를 나눈다.
- 다른 세션이 소유한 파일을 고쳐야 하면 먼저 PM에게 알린다.
- `git commit`은 PM이 자주 수행한다 (씬 수정 전엔 반드시).
- **`git push`는 PM만 한다.** 팀원은 커밋까지만 하고 푸시하지 않는다.

```

```

## 커밋 전 점검 (PM)

**커밋 전에 이거 하나를 돌린다.** 아래 다섯 검사를 전부 묶어 놨다:

```
Tools/check_all.sh          # 전부
Tools/check_all.sh --fast   # C# 컴파일(제일 느림)만 건너뜀
```

🔴 **2026-09-08 사고**: 이 절에 「.meta를 꼭 확인해라」가 이미 적혀 있었는데도
**스킨 파일 44개가 .meta 없이 커밋돼 있었다.** 다른 컴퓨터에서 클론하면 참조가 전부
끊기는 상태였고, 이 컴퓨터에서만 멀쩡해 보였다. `check_all.sh`를 만들어 처음 돌리자마자
잡혔다. **규칙을 적어 두는 것과 실제로 돌리는 것은 다르다** — 그래서 하나로 묶었다.

아래는 개별 검사의 배경이다(무엇이 왜 위험한지 알아야 결과를 읽을 수 있다).

**코드를 고친 뒤**:

```
Tools/compile_check.sh
```

컴파일이 실패하면 Unity는 **마지막으로 성공한 어셈블리를 그대로 유지한다.**
메뉴도 옛 코드로 계속 동작하므로, 겉보기에는 "고쳤는데 반영이 안 된다"로만 보인다.
실제로 이 함정에 두 번 빠졌고, 두 번 다 원인을 찾는 데 오래 걸렸다.

새 스크립트나 에셋을 만든 뒤에는 **푸시 전에 반드시** 실행한다:

```
python3 Tools/check_meta.py
```

`.meta`에는 GUID가 들어 있고 씬은 컴포넌트를 그 GUID로 참조한다.
`.meta` 없이 커밋하면 다른 컴퓨터에서 클론했을 때 Unity가 새 GUID를 발급하고,
그 스크립트를 쓰는 씬 참조가 전부 Missing Script가 된다.

Unity가 `.meta`를 만드는 시점이 스크립트를 만든 직후가 아니라 **에디터가 임포트할 때**라,
`git add`를 먼저 하면 매번 놓친다. 실제로 세 번 놓쳤다.

## 커밋은 반드시 pathspec 형태로

```
git diff --cached --name-only          # 먼저 눈으로 확인
git commit -m "..." -- 파일1 파일2      # -- 뒤에 경로를 나열
```

`git add` 뒤 `git commit`을 쓰면 **인덱스 전체**가 커밋된다.
여러 세션이 한 저장소를 쓰는데 **인덱스는 세션끼리 공유되므로**,
다른 세션이 같은 순간에 스테이징해둔 파일까지 같이 들어간다.
파일을 하나씩 `add`해도 이걸 못 막는다 — 막는 건 `--` 뒤의 경로 목록뿐이다.

2026-09-02에 실제로 났다. PM의 도박소 수정 커밋이 구현담당1의
`RoundManager.cs`·`MapGenerator.cs`·`Traits.meta`를 통째로 삼켰다.
코드는 안 날아갔지만 그 변경의 커밋 메시지가 사라져서,
나중에 이력을 읽는 사람이 왜 들어갔는지 알 수 없게 됐다.

**새 파일이 있으면 두 단계다.** 추적되지 않는 파일은 pathspec에 안 잡혀서
`git commit -- <새파일>`이 통째로 취소된다. 새 파일만 먼저 넣고 커밋한다:

```
git add -- 새파일1 새파일2
git commit -m "..." -- 새파일1 새파일2 고친파일1
```

`add`에도 `--` 뒤에 파일을 나열하는 건 같다. 보호 효과는 그대로다 —
커밋 범위를 정하는 건 여전히 `commit`의 `--` 뒤 목록이다.

`git add <디렉터리>`는 여전히 금지다. 그건 **내가 의도하지 않은 파일**을 막는 규칙이고,
이건 **남이 스테이징한 파일**을 막는 규칙이다. 둘 다 필요하다.


## 「완료」는 코드가 아니라 도달로 증명한다

**코드 경로가 있다고 도달하는 건 아니다.** 2026-09-04에 같은 함정을 하루에 세 번 밟았다:

1. `MobPrefab.damageTable`이 한 번도 배선된 적 없어 `null` — **배율표 전체가 곱해지지 않고 있었다.** 그 사이 PM은 "이번엔 진짜 동작이 바뀝니다"를 세 번 말했다
2. `PlayerContext.unitUpgrades`가 씬 4개 전부 `{fileID: 0}` — 유닛강화소 12개가 서 있는데 안 눌린다
3. **2번을 찾은 사람이 곧바로** "배선하면 다섯이 살아난다"고 보고했는데, 재보니 전투 수치는 하나도 안 바뀐다(특성 효과가 `unlockedTraits`에 매달려 있고 `Unlock()`을 부르는 코드가 없다). PM도 검증 없이 그대로 사장님께 옮겼다

**그러니 「완료」라고 쓰기 전에 셋을 다 확인한다:**

```
1. 코드가 있는가
2. 데이터(에셋)가 있는가
3. 둘이 실제로 연결돼 있는가      ← 1·2만 보면 위 셋을 다 놓친다
```

**3번은 「끝까지 따라가서」 확인한다.** 값이 흘러 실제로 곱해지는 지점까지 가야 한다. 중간에 빈 컬렉션·null·안 불리는 메서드가 하나라도 있으면 도달이 아니다.

**필드 단위 결측(2번, "데이터가 있는가")은 `Tools/audit_data.py`로 훑는다.** 2026-09-05에
도움소·적·유닛·조합식 필드 감사를 세 번 손으로 돌렸는데 매번 스크립트를 새로 짜고 지웠고,
그중 한 번은 리스트 내부 필드(`count:` 등)를 최상위로 잘못 세는 실수를 했다. 이 스크립트는
읽기 전용이고 값을 하드코딩하지 않는다(`Tier()`도 `UnitData.cs`에서 직접 파싱) — 매번 새로
짜지 말고 이걸 돌린다. 다만 "읽힘/누락/미사용"까지만 자동으로 낸다 — "이 필드는 특정 조건
에서만 쓰인다(해당없음)"는 사람이 코드를 읽고 판단해야 한다.

**값을 바꾸면 그 값이 적힌 문서를 같이 고친다.** 2026-09-05에 도움소 4~5종 값이 원작값으로
정정됐는데 `SUPPORT_SHOP.md`의 "우리 구현과 다른 점" 열이 옛 값 기준으로 남아 있었다 —
차이가 이미 없어졌는데 "차이 있음"으로 읽혀서, PM이 그걸 보고 이미 끝난 일을 다시 지시할
뻔했다. **문서를 지우지 말고 "언제 무엇으로 바뀌었다"를 이어 붙인다** — 지우면 그 문서가
왜 한때 다른 값을 적어뒀는지(조사 당시의 근거)가 같이 사라진다.

### 주석은 증거가 아니다

`UnitUpgradeShop.cs:9`가 *"`UnitAttacker`가 `UnitUpgrades.MultiplierFor(grade)`를 부른다"*고 적어 뒀는데 **`MultiplierFor`는 존재하지 않는 메서드다.** 주석이 없는 코드를 설명하고 있었고, 그걸 믿은 사람들이 "연결돼 있구나" 하고 지나갔다.

**「A가 B를 부른다」는 주석을 보면 B가 실재하는지, 부르는 곳이 있는지 확인한다.** 틀렸으면 그 자리에서 고친다 — 죽은 배선을 살아 있다고 말하는 문장이 제일 비싸다.

### 위험한 건 「없는 것을 가리키는 주석」이 아니다

주석 1,837줄을 기계로 훑었더니 **없는 멤버를 가리키는 건 딱 하나**였다. 정말 위험한 건 이쪽이다:

> **지목한 심볼이 전부 실재하는데, 그 사이 길이 끊긴 주석**

`UnitTraitData.cs:7-8`이 *"`ArmorShred`는 살아났다 — `EnemyDummy.AddArmorShred`로 쌓인다"*고 적어 뒀는데, 지목한 `ApplyArmorShred`·`ResolveUpgrades`·`EffectSum`·`AddArmorShred`가 **전부 실재한다.** 끊긴 건 그 사이 두 군데다(`unitUpgrades`가 null, `unlockedTraits`가 빈 집합).

**이건 스캔으로 안 나온다. 경로를 손으로 끝까지 따라가야 나온다.** 그러니 기계 검사를 돌렸다고 "전부 훑었다"고 쓰지 말 것 — **어느 계통을 손으로 따라갔는지**를 밝힌다.

### 죽어 있는 게 나은 경우가 있다

배선을 살리면 **유닛강화소가 12,000엔을 받고 아무것도 안 주게 된다**(올린 레벨을 읽는 코드가 없다). **「안 눌린다」보다 「돈을 먹고 속인다」가 나쁘다.** 배선 전에 "살리면 무엇이 어떻게 되는가"를 재고, 나빠지면 넣지 않는다.

### 「검산했다」가 순환논증일 수 있다

`EnemyDummy.cs:175`에 이렇게 적혀 있었다:

> *"원작이 워크3 시스템을 그대로 쓴다 — 「방어력 −20이면 71% 추가 피해」가
> `2 − 0.94^20 = 1.7099`와 정확히 맞는다(UNIT_STATS_RESEARCH 검산)"*

**검산이 아니었다.** `0.94`는 `1 − 0.06`이라, **공식이 0.06이라는 가정을 스스로 되풀이한 것**뿐이다.
서로 다른 두 출처가 맞아떨어진 게 아니라 **같은 가정이 두 번 나왔다.**
그리고 원작 맵은 실제로 `DefenseArmor=0.02`였다 — 그 「검산」은 이 맵을 확인해 준 적이 없다.

**「검산 완료」라고 적힌 주석이 제일 위험하다.** 다음 사람이 거기서 멈추기 때문이다.
검산을 적을 때는 **두 출처가 독립인지** 밝힌다: 무엇과 무엇을 맞춰봤는지, 그 둘이
같은 가정에서 나온 게 아닌지. 아니면 「검산」이라 쓰지 않는다.

2026-09-04에 이 정정이 선 이유가 그거다 — **계산**(71%는 K=0.06에서만 나오는 수)과
**검색**(맵 텍스트 전수 0건)이 **각각 독립으로** 도달했다. 한쪽만이었으면
"우리가 잘못 읽었나"로 남았을 것이다.

|---|---|
| 「와포루 성공 시 스토리에 450만 마법피해」를 만들라고 지시 | **원작 트리거에 피해 호출이 0건.** 툴팁만 있고 배선이 없다 |
| 「스모커 보상 5,000골드」 | 원작도 코드도 **3,000**. 문서의 오기 |
| 「와포루는 21~30라운드」 | 툴팁뿐. **트리거는 시작부터 재고에 넣고 31라운드에 뺀다** |
| 「드레스로사 12,500골드」 | 실제 지급 호출은 **10,000** |

**원작 툴팁은 원작 동작이 아니다.** 워크3 맵 제작자도 툴팁과 트리거를 따로 쓰고,
고치다 만 것이 그대로 남는다. **판정은 언제나 트리거·오브젝트 데이터 쪽이다.**

**막는 방법:** 지시문이나 커밋에 숫자나 「원작은 이렇다」가 들어가면 **근거가 문서인지 원문인지 밝힌다.**
문서면 그 항목만이라도 원문을 다시 연다. 문서는 그때의 이해고, 코드가 바뀌면 문서만 남는다.

### 뿌리 ② 전제가 폐기됐는데 그 위에 쌓은 것이 남아 있었다

「원작 수치를 우리 스케일로 옮기는 환산법」으로 도움소 값 넷을 계산했는데,
**그 계산 23분 뒤에 적 로스터가 통째로 원작값으로 교체돼 환산이 불필요해졌다.**
아무도 옛 계산을 다시 보지 않아서 **낙뢰가 42배, 독약이 69배, 미니보스 HP가 29배 작은 채로** 남았다.

**막는 방법:** 「A라서 B로 했다」를 커밋에 적을 때 **A를 검증 가능한 형태로** 적는다
(어느 파일의 어느 상수인지). 그리고 **A를 바꾸는 커밋을 할 때 B를 검색한다.**
문서는 결론을 절차보다 **위에** 쓴다 — 절차만 남으면 다음 사람이 폐기된 절차를 따라 한다.

### 뿌리 ③ 「없다」의 탐색 범위가 좁았다

| 무엇 | 실제 |
|---|---|
| `StoryRewardData`는 참조 0건이니 지워도 된다 | **같은 파일 안에 6개 파일이 쓰는 `WispReward`가 있었다.** 지우자 컴파일이 깨졌다 |
| 초월위습은 조합식 결과도 아니고 뽑기에도 없으니 획득 불가 | **씬의 `UnitPortal`이 `specificUnit`으로 지급한다.** 에셋만 봤고 `.unity`를 안 봤다 |
| `critDamageMultiplier`가 238종 전부 1.0이니 결측이다 | **설계 문서가 제시한 두 안 중 하나를 택한 것.** 채웠으면 배수가 두 번 곱해졌다 |

**막는 방법:** **「어디에도 없다」를 쓸 때 무엇을 봤는지 같이 쓴다** — 에셋만인지, 씬·프리팹까지인지,
설계 문서까지인지. 범위를 안 밝힌 「없다」는 결론이 아니라 **그 범위 안에서의 관찰**일 뿐이다.
그리고 파일을 지우기 전엔 **파일이 아니라 그 안의 심볼 단위로** 참조를 센다.

### 뿌리 ④ 「했다」가 도달을 뜻하지 않았다

- `8dccf11`이 「해적단 퀘스트 계통 **구현**」이라 적었지만 **`MapGenerator`에 진입점이 없어 씬에 아예 안 붙었다.**
- `ffa10d5`가 「**239종 값**」이라 적었지만 네 축 중 하나는 안 채워졌다.
- 폭우가 `waveCount` 필드 자체가 에셋에 없어 **3웨이브가 아니라 1회성으로** 돌고 있었다.

**막는 방법:** 커밋 메시지에 **「구현」·「완료」·「N종 값」을 쓰기 전에 셋을 확인한다** —
코드 / 데이터 / **씬에서 이어지는가**. 셋째를 못 봤으면 **「미도달」이라고 함께 적는다.**
그리고 값 대조로는 **필드가 통째로 없는 것**을 못 잡는다 — 「필드 × 에셋 격자」로 따로 훑어야 한다
(그날 폭우가 그렇게 걸렸고, 조합식 12개의 YAML 들여쓰기 깨짐도 같은 방식으로 나왔다).

### 그리고: 되돌려주는 사람이 일을 제대로 한 것이다

그날 팀원이 **「이미 됐습니다」·「원작에 없습니다」·「제 헤드라인이 틀렸습니다」**로 세 번 돌려세웠고,
세 번 다 맞았다. **지시를 받은 쪽이 착수 전에 확인하는 것이 마지막 안전망**이다 —
지시가 근거를 밝히지 않았으면 물어보고, 확인해서 다르면 그대로 보고한다.
